* **Ansible collections** are a packaging format that bundles **roles, modules, plugins, playbooks, and docs** together as a single, versioned unit
* They solve problems like:
  * namespace conflicts (same module name from different vendors)
  * easier sharing and versioning
  * clean separation between core Ansible and community/vendor content

* Collections are referenced using a **namespace.collection_name** format (example: `community.general`)
* **Why collections exist (simple view)**
  * Before: everything lived in `/roles`, `/library`, `/filter_plugins` → messy
  * Now: everything is namespaced and self-contained
  * You can install, upgrade, downgrade collections independently

* **Basic collection naming rules**
  * `namespace`: usually your org/user name (lowercase)
  * `collection`: project name (lowercase)
  * Example: `myorg.linux_admin`

* **Standard collection directory structure**
  * `ansible_collections/`
    * `namespace/`
      * `collection_name/`
        * `galaxy.yml` → metadata (name, version, author, deps)
        * `README.md`
        * `roles/`
          * `role1/`
            * `handlers/main.yml`
            * `defaults/main.yml`
        * `plugins/`
          * `modules/`
          * `filter/`
          * `lookup/`
          * `callback/`
        * `playbooks/`
        * `docs/`
        * `tests/`

* **Important files explained**
  * `galaxy.yml`
    * collection name, version, description
    * supported Ansible versions
    * dependencies on other collections
  * `roles/`
    * normal Ansible roles, nothing special
  * `plugins/modules/`
    * custom Python modules
  * `plugins/filter/`
    * Jinja2 filters
  * `playbooks/`
    * reusable example or utility playbooks

* **How to create a collection (recommended way)**
  ```bash
  ansible-galaxy collection init myorg.linux_admin
  ```

  * This automatically creates:
    * correct directory structure
    * `galaxy.yml`
    * skeleton folders

* **Where collections live on a system**
  * User level:
    * `~/.ansible/collections/`
  * System level:
    * `/usr/share/ansible/collections/`
  * Project local (best practice for DevOps):
    * `./collections/ansible_collections/`

* **Using a role from a collection**
  ```yaml
  - hosts: all
    roles:
      - myorg.linux_admin.common
  ```

* **Using a module from a collection**
  ```yaml
  - name: Create user
    myorg.linux_admin.user_manage:
      name: devops
  ```

* **Installing a collection**
  ```bash
  ansible-galaxy collection install myorg.linux_admin
  ```

* **Installing from requirements file**
  ```yaml
  collections:
    - name: myorg.linux_admin
      version: "1.0.0"
  ```

  ```bash
  ansible-galaxy collection install -r requirements.yml
  ```

* **Building and publishing a collection**
  ```bash
  ansible-galaxy collection build
  ansible-galaxy collection publish myorg-linux_admin-1.0.0.tar.gz
  ```

  * Usually published to Ansible Galaxy or a private automation hub

* **Best practices**
  * Keep one purpose per collection
  * Version collections semantically (1.0.0, 1.1.0)
  * Don’t mix unrelated roles
  * Pin collection versions in production
  * Store collections inside the repo for CI/CD
